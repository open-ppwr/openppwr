# Dossier artifact integrity and provenance

What the checksum manifest proves, what it does not, and why the artifacts are not digitally signed.

Status: decided 2026-08-01 for OpenPPWR Community `0.2.0-beta.1`. This is a scope decision, not a
deferral — the conditions that would reopen it are listed at the end.

## What is produced

Generating a dossier from a frozen review snapshot produces four artifacts, described in
`DOSSIER_SCHEMA.md`:

| Artifact | What it is |
| --- | --- |
| `dossier.json` | The canonical, key-sorted machine record |
| `dossier.pdf` | The human summary rendered from the same snapshot |
| `checksum-manifest.json` | SHA-256 and byte length for every file in the package, in stable order |
| `dossier.zip` | JSON, PDF, evidence bytes and the manifest, packaged deterministically |

## What the manifest proves, and to whom

The manifest answers one question completely: **do the bytes in this package still match the bytes that
were packaged?** Anyone holding the ZIP can recompute the digests and find out, with no key, no network
call and no trust in anything except SHA-256.

It cannot answer a different question: **who produced this?** A recipient who received the package from
somewhere other than the operator could edit the JSON, recompute the manifest and hand on something
internally consistent and false. A manifest travels with what it describes, so it is only ever as
trustworthy as the channel that delivered both.

That gap is real, and the obvious remedy is a digital signature. The remedy was examined and rejected.

## Why the artifacts are not signed

### There is no relying party who could verify one

A signature is only worth what its verification is worth, so the question is not "would a signature be
better in principle" but "who would check it, against which key, and where would they get that key?"

A dossier is generated by an operator's own self-hosted deployment and handed by that operator to a
regulator, an auditor or a customer. The recipient's confidence in it comes from the operator who handed
it over — it arrived through a channel they already trust, from an organisation that is accountable for
its contents. Nothing about a signature adds to that, because there is no key the recipient could
independently associate with that operator.

Walk through the alternatives and each one closes:

- **The verification key ships inside the ZIP.** Then it proves the package is self-consistent, which is
  what the manifest already proves. Anyone who can alter the artifacts can alter the key beside them.
- **The operator publishes their key somewhere.** Now every self-hoster has to run and maintain a
  publication point, and every recipient has to decide whether the page they found is really that
  operator's. A recipient who can already authenticate the operator's website could just as well have
  been given the dossier through it.
- **OpenPPWR issues or certifies the keys.** This is the only version where a recipient has something to
  check against, and it is the one version the product cannot have. It would make every self-hosted
  deployment enrol with a service we operate, contradicting the property the product exists to offer —
  a Community deployment that sends us nothing at all — and would make us an authority on identities we
  have never verified.

The honest conclusion is that the signature would be generated, and nobody would ever verify it.

### Key management decides it, exactly as it did for backups

The comparable problem in this product is backup encryption, where the same question — where does the
key live — is what made the design work: the private key is generated once, refused a home anywhere
under the deployment root, and carried off the host by the operator, because a key stored beside the
thing it protects protects nothing. See `../deployment/BACKUP_RESTORE_UPGRADE.md`.

Signing has the same constraint and none of the same answers:

- A signing key beside the artifacts it signs proves nothing, for the same reason as above.
- A signing key that exists only where the operator keeps it introduces a failure the backup key does
  not have. A dossier is retained for years and read long after it was produced. A key that is lost,
  rotated or replaced when the deployment is rebuilt takes with it the ability to verify every dossier
  already delivered — so signing would require a published, retained key **history**, which is a
  key-management obligation placed on every self-hoster in service of a verifier who does not exist.

### It is not the signature that would carry weight anyway

OpenPPWR does not produce, and does not attempt to substitute for, a signature that carries legal effect.
Where a person or an organisation has to sign or seal a document, they sign it, under whatever framework
applies to them. A signature applied by the tool that generated the file would sit beside that one and
could be mistaken for it — a worse outcome than not signing at all. Every dossier states that it makes no
claim of guaranteed or certified compliance, and a cryptographic flourish that reads as an assurance
works against that statement.

## What does answer a provenance question today

A recipient who needs more than the manifest does not need a signature; they need the operator's records,
and the deployment keeps them:

- **The digest of every artifact is recorded when it is generated**, in the deployment's own database and
  in a `dossier.generated` audit event carrying each artifact's type, SHA-256 and size.
- **The audit log is hash-chained and append-only.** Each event carries the hash of the one before it,
  the database refuses `UPDATE`, `DELETE` and `TRUNCATE` on it by trigger, and the chain can be verified
  on demand. A digest recorded there cannot be quietly changed later to match an altered file.
- **The review snapshot is verified against its own recorded digest before anything is built from it**, so
  a dossier cannot be generated from a snapshot that no longer matches what was frozen.
- **Generation is deterministic and replayable.** The same frozen snapshot regenerates the same bytes, and
  a request to generate again returns the artifacts already persisted rather than making new ones.

So a challenged dossier is settled by asking the operator to show the digest in their own audit chain and
regenerate the artifact from the snapshot — evidence that is available to an auditor with access to the
deployment, which is exactly the party who would ever push a challenge that far. A signature would have
told the same person something they can already establish, and told everyone else nothing.

## What would reopen this

The decision is scoped to a self-hosted deployment handing artifacts to a party that already trusts it.
Any of the following breaks that assumption and the question should be asked again:

1. **A managed deployment generates dossiers on a customer's behalf.** Then there is one operator, with
   one key, publishable at one well-known location, and a genuine relying party: the customer verifying
   what their provider produced for them.
2. **A recipient states a verification requirement.** A regulator, auditor or customer who says which
   signature format they check and how they obtain keys has supplied the two answers missing above.
3. **Artifacts start reaching recipients other than by the operator's own hand** — a shared portal, a
   third-party exchange, a public register — so that the channel is no longer the thing carrying the
   trust.

Until one of those holds, the artifacts carry an integrity manifest and no signature, and that is a
decision rather than an omission.
